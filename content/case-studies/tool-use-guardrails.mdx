## Problem / Goal

When LLMs are granted access to external tools (SQL databases, payment APIs, system command execution), probabilistic hallucination becomes a major security liability. A single prompt injection payload or malformed function call can drop production tables or exfiltrate private credentials.

The goal was to engineer a **Deterministic Tool-Use Security Proxy** that sits between the LLM agent and external tool APIs, validating payloads against strict JSON schemas and enforcing role-based access control (RBAC) in sub-15ms latency.

---

## Architecture Overview

The system operates as a reverse proxy gateway where all agent tool calls must pass through a **Deterministic Security Gateway** before execution.

![Deterministic Guardrails & Policy Enforcement Proxy Architecture](/diagrams/tool-use-guardrails.png)

### Proxy Verification Pipeline

1. **Schema Validation Layer**: Enforces strict JSON Schema invariants (required keys, regex patterns, number boundaries) using Rust-powered validation bindings.
2. **Injection & Exfiltration Firewall**: Analyzes tool call arguments for SQL injection sequences, path traversals (`../../`), and SSN/API key leakage.
3. **Sandbox Policy Engine**: Evaluates permissions against an Open Policy Agent (OPA) policy file before forwarding requests to the downstream API.

---

## Tech Stack Used

- **API Gateway**: FastAPI (Python 3.12) with Pydantic v2 and Rust JSON Schema validators
- **Policy Engine**: Open Policy Agent (OPA) & Rego syntax
- **Audit Storage**: PostgreSQL with immutable append-only audit logs
- **Load Testing**: Locust for latency benchmarking at 2,500 req/sec
- **Deployment**: Docker container deployed on AWS ECS Fargate

## What Broke / Failure Modes Encountered

<FailureModeAlert title="High Latency Tail Overhead & Schema Hallucinations" severity="critical">
When the LLM generated deeply nested JSON payloads containing markdown code fences or trailing commas, the Pydantic v1 validator rejected the request with cryptic syntax errors. The agent would then attempt 5+ fallback retries, causing end-to-end tool calling latency to balloon from 400ms to over 4 seconds.
</FailureModeAlert>

### Additional Failure Modes
- **Over-Aggressive Blocking**: Early regex filters for SQL injection flagged benign user queries like `"Select a table from the restaurant menu"` as malicious database commands.
- **Context Bleed**: Error messages returned to the LLM when a tool call failed contained internal stack traces that the LLM subsequently leaked into user responses.

---

## How It Was Fixed / Lessons Learned

1. **Deterministic JSON Repair Pre-Processor**:
   - Integrated a lightweight syntax normalizer that strips stray markdown quotes, fixes trailing commas, and coerces stringified numbers before schema validation.
2. **Context-Aware Semantic Policy Checks**:
   - Replaced naive regex blocking with AST-level SQL query parsing for database tools, ensuring only syntactically executable DDL/DML statements trigger security alerts.
3. **Sanitized User-Facing Exceptions**:
   - Stripped all internal exception paths from proxy error messages, returning clean, actionable guidance to the LLM (e.g., `Error: parameter 'date' must format as YYYY-MM-DD`).
